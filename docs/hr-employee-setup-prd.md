# 執行 PRD：HR 員工設定

## 1. 目的

HR 員工不是另一套帳號，而是既有平台使用者（`users`）的人事延伸。HR 管理者從既有使用者選擇帳號，建立員工關聯與第一段任職資料。

```text
users 1 ─── 0..1 hr_employees 1 ─── N hr_employments
```

- `users` 是姓名、Email 與帳號狀態的唯一來源。
- `hr_employees` 保存員工編號、主管等員工層級資料。
- `hr_employments` 保存每一段任職／復職期間。
- 所有薪資、出勤、假勤與獎金資料應關聯 `employmentId`，不能只關聯 user。
- 帳號狀態與任職狀態分開管理；停用帳號不代表離職。

## 2. 核心產品決策

1. 待啟用的 User 可以先指派為員工。
2. 主管不在第一次指派時設定，建立員工後從各自的員工資料管理入口設定。
3. 第一次任職建立時出勤設定預設為「一般辦公」；出勤方式由「出勤／出勤範圍管理」統一設定。
4. 員工編號由 HR 手動輸入，且全平台唯一。
5. 所有員工都可以指定一個或多個辦公位置；辦公位置指派集中在「出勤／出勤範圍管理」，排班只負責每日工作地點與班別安排。
6. 員工列表以「在職／未在職」分頁呈現任職關係；未在職包含已離職與尚未到職者。
7. 任職新增、復職與結束任職會留下可供 HR 復原的最近一次操作；日期修正會遞增 revision 並留下欄位級稽核；日期修正也受既有歷史邊界與版本檢查保護。
8. 輸入錯誤的任職可由 HR 撤銷；撤銷保留任職列、`employmentId` 與所有下游歷史，不 cascade 刪除或改寫關聯資料。

## 3. 本功能範圍

### 包含

- 從既有 User 候選清單指派員工。
- 建立第一段任職紀錄。
- 查看出勤方式。
- 查看與搜尋員工。
- 查看員工內頁。
- 設定主管（從既有主管管理入口維護）。
- 新增任職／復職。
- 修正任職到職日與年資認列日；新的到職日不得晚於既有下游歷史的起始日。
- 結束任職。
- 撤銷輸入錯誤的任職，保留任職列與所有下游歷史。
- 復原該員工最近一次任職操作（仍符合版本與操作順序時）。

### 不包含

建立員工時不設定：

- 薪資與勞健保
- 營運據點歸屬
- 辦公位置
- 排班
- 獎金
- 請假與加班

這些資料在員工建立後，從各自的 HR 管理頁設定；辦公位置與出勤方式在「出勤／出勤範圍管理」設定，每日工作地點與班別在「排班／排班月曆」設定。

## 4. 導覽與頁面

```text
HRIS
└─ 員工管理
   ├─ 員工列表
   └─ 員工內頁
```

### 員工列表

- 頁面標題：員工列表
- 右上角主要操作：指派員工
- 搜尋：姓名、員工編號、Email
- 第一層分頁：任職狀態
  - 在職：今天落在任職區間 `[hiredOn, endedOn)` 內。
  - 未在職：已離職、尚未到職，或沒有有效任職。
- 篩選：帳號狀態（全部、啟用中、待啟用、已停用）。
- 欄位：員工編號、姓名、Email、帳號狀態、任職狀態。
- 支援排序與分頁；分頁數字依目前搜尋與帳號篩選計算，仍同時顯示在職／未在職計數。
- 點擊整列進入員工內頁；列上的「管理任職」入口開啟只處理任職關係的 Dialog，不進入內頁操作。

帳號狀態與任職狀態必須分開顯示：

| 狀態 | 來源／判斷方式 |
|---|---|
| 帳號狀態 | `users.status` |
| 任職狀態 | 依 `hr_employments` 與目前日期計算 |

停用帳號不等於刪除員工，也不等於刪除任職歷史。

## 5. 指派員工 Dialog

### 欄位

| 欄位 | 必填 | 規則 |
|---|---:|---|
| 使用者 | 是 | 從尚未成為員工的 User 選擇 |
| 員工編號 | 是 | 手動輸入，1～40 字元，全平台唯一 |
| 到職日 | 是 | 第一段任職起日 |
| 年資認列日 | 是 | 預設等於到職日，不得晚於到職日 |

使用者選項顯示：

```text
王小明（wang@example.com）
```

姓名與 Email 只讀，不複製到 `hr_employees`。

### User 候選條件

- `users.status` 為 `active` 或 `invited`。
- 尚未存在 `hr_employees` 關聯。
- 不提供在此建立新 User 的功能。
- 沒有候選人時顯示前往使用者管理邀請帳號的提示。

### 建立操作

指派員工必須以同一個原子操作建立：

1. `hr_employees`
2. `hr_employments`
3. `hr_employment_attendance_settings`

任何一步失敗，整次操作不得留下半套員工資料。

建立成功後列表會重新整理並提供「復原上一動」；可點選整列進入：

```text
/hr/employees/:userId
```

## 6. 員工內頁

### 基本資料

顯示：

- 姓名：來自 `users`
- Email：來自 `users`
- 帳號狀態：來自 `users`
- 員工編號：來自 `hr_employees`
- 主管：可顯示尚未設定
- 任職狀態：依 Taipei 當地日期與任職區間計算；不以帳號停用狀態代替。

### 任職資料

每一段任職顯示：

- 到職日
- 不再任職首日
- 年資認列日
- 出勤方式

員工內頁只呈現資料，不提供資料異動按鈕。任職／復職、結束任職與任職中途的指派調整，都從員工列表列上的「管理任職」入口開啟 Dialog；結束任職時，仍有效的營運據點歸屬與辦公位置指派會自動在離職生效日結束並保留歷史；辦公位置與出勤方式的完整設定從「出勤／出勤範圍管理」維護，薪資與勞健保從各自管理頁維護。

員工內頁採互斥 Accordion；一次只展開一個資料區塊。

### 辦公地點摘要

所有員工不論出勤方式，都可以指定一個或多個有效辦公位置；實際新增、移除與日期設定統一在「出勤／出勤範圍管理」操作。

員工內頁只顯示：

- 目前有效辦公位置。
- 各位置生效期間。
- 出勤範圍管理所保存的歷史摘要。

結束任職時，系統會自動把仍有效的辦公位置指派收合到離職生效日；任職中途要轉換位置時，管理任職 Dialog 可提供「結束指派」，完整出勤方式與位置編輯仍在「出勤／出勤範圍管理」。

一般辦公員工以有效辦公地點作為可打卡地點範圍。排班員工的每月休假天數在出勤範圍管理設定，實際每日工作地點與班別則使用「排班管理／排班月曆」設定。

## 7. 任職與復職規則

### 結束任職

`endedOn` 表示「不再任職的第一天」，採半開區間 `[hiredOn, endedOn)`。

例如：

```text
hiredOn: 2026-01-01
endedOn: 2026-08-01
```

最後工作日為 2026-07-31。

結束任職時，系統會在同一交易自動把超出離職日期的：

- 營運據點歸屬（員工在某個門市／營運單位的工作歸屬）
- 辦公位置指派（員工可在哪個位置打卡）

設定 `validTo` 為離職生效日。這不是刪除歷史；營運據點歸屬與辦公位置指派都保留原列。若只是任職中途調整指派，才使用個別的「結束」操作。

### 復職

不可把舊任職的 `endedOn` 清空。復職必須新增另一筆 `hr_employments`。

```text
同一 User
  └─ 同一 hr_employee
       ├─ employment A：已結束
       └─ employment B：復職後新任職
```

同一 User 的任職期間不可重疊。

### 撤銷錯誤任職

任職 Dialog 的每段任職都提供「撤銷這段任職」。撤銷不是物理刪除，而是在 `hr_employments` 記錄 `revokedAt`／`revokedBy`，保留原列、`employmentId` 與稽核歷史；撤銷後該列不再參與在職狀態、任職重疊與新的下游資料關聯。

任職撤銷不是物理刪除，也不會 cascade 刪除或改寫營運據點、辦公位置、打卡、薪資、勞健保、假勤、申請、排班、獎金或薪資結算等下游歷史。撤銷後該任職不再參與在職狀態、任職重疊、薪資與新的下游資料關聯；既有關聯只作為歷史保留。若要重新加入，應建立新的任職版本；若只是要表示正常離職，應使用「結束任職」，讓指派期間同步收合。

### 最近一次操作復原

- 指派員工、建立任職／復職與結束任職會寫入 `hr_employment_actions`；修正任職日期會留下前後日期的欄位級稽核與新的 revision。
- Dialog 與成功提示可提供「復原上一動」；只接受該員工仍是最近一筆任職操作，且資料 revision 未被後續修改的操作。
- 結束任職的復原會重新開啟同一筆歷史任職，並恢復同批自動收合的指派期間與主要辦公位置 pointer，再遞增 revision。
- 新增任職的「復原上一動」、任職日期的稽核與錯誤任職的「撤銷這段任職」都不物理刪除已有歷史資料；撤銷使用獨立的 `revokedAt`／`revokedBy` 狀態。
- 衝突時保留原資料並顯示：`這筆任職資料在復原前已被其他人修改，請重新整理後確認。`

## 8. 主管設定

主管從既有 HR 員工中選擇：

- 必須是啟用中的 User。
- 不可設定自己為主管。
- 可清除主管。
- 主管設定保存於 `hr_employees.supervisor_user_id`。
- 補打卡與其他申請可使用該主管作為預設審核者。

## 9. 權限

| 操作 | 權限 |
|---|---|
| 查看員工列表與基本資料 | `hr:employee:read` |
| 指派員工 | `hr:employee:write` |
| 編輯員工編號 | `hr:employee:write` |
| 設定主管 | `hr:employee:write` |
| 新增任職／復職 | `hr:employee:write` |
| 修正任職日期 | `hr:employee:write` |
| 結束任職 | `hr:employee:write` |
| 結束營運據點歸屬 | `hr:employee:write` |
| 結束辦公位置指派 | `hr:office:write` |
| 撤銷錯誤任職 | `hr:employee:write` |
| 復原最近一次任職操作 | `hr:employee:write` |

薪資、勞健保、請假與打卡明細另依敏感資料權限限制，不因可以查看員工基本資料而自動開放。

## 10. 失敗狀態

UI 必須能顯示後端明確錯誤：

- 使用者已經是員工。
- 員工編號已被使用。
- 使用者不存在或帳號狀態不允許。
- 到職日與年資認列日不合法。
- 任職期間重疊。
- 資料已被其他人修改，要求重新整理。
- 任職復原不是該員工最近一次操作，或 revision 已被後續變更。
- 任職撤銷會保留原任職的下游關聯作為歷史；原任職撤銷後不得新增關聯，重新加入應建立新的任職；若只是要離職，直接結束任職，系統會自動結束仍有效的指派。
- 沒有符合條件的 User 候選人。

員工資料與任職資料不提供物理刪除按鈕。

## 11. UI 設計要求

- 列表使用 `.page.fills`、`.panel.grows`。
- 搜尋與篩選使用 compact toolbar。
- 表格使用既有 `.data-table` 與 sticky header。
- 任職與必要的指派結束操作集中在 Dialog，不在表格列內展開表單；表格列只保留「管理任職」入口。
- 手機版使用 `data-label` 呈現表格欄位名稱。
- 姓名／Email 等 User 欄位不可在 HR 表單重複編輯。
- 重要異動需保留 revision、操作紀錄與可復原的操作索引。

## 12. 驗收條件

- 可以從 active 或 invited User 建立員工。
- 同一 User 不可重複指派。
- 員工編號不可重複。
- 姓名與 Email 永遠顯示 User 的最新資料。
- 建立員工會同時產生第一段任職與出勤設定。
- 建立任職時預設出勤方式為一般辦公；排班方式與每月休假天數在「出勤／出勤範圍管理」設定。
- 待啟用 User 可被建立，但尚未啟用前不應進入正常薪資計算。
- 停用 User 不會刪除員工與歷史任職。
- 離職保留舊任職，復職建立新任職。
- 主管不可指定自己。
- 任職期間不可重疊。
- 在職／未在職分頁依 Taipei 當地日期正確篩選，帳號狀態與任職狀態分開。
- 結束任職會自動將超出離職日的營運據點歸屬與辦公位置指派收合至離職生效日，保留原列與歷史。
- 任職可以修正到職日與年資認列日，會遞增 revision 並留下前後值稽核；新的到職日若晚於既有下游歷史起始日，API 會拒絕改寫。
- 最近一次新增／結束任職操作可在沒有後續修改時復原；衝突不會覆蓋新資料。
- 輸入錯誤的任職可撤銷，且保留 `employmentId` 與所有下游歷史；撤銷後可重新建立正確任職。
- 任一建立步驟失敗時，不留下半套資料。
