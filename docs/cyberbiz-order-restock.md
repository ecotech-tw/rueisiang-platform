# CYBERBIZ 官網訂單回補

本文說明實作的責任邊界與安全限制；正式庫存寫入需要另行核准 rollout，不能由本機測試推定為已驗證。

## 業務邊界

現場在 CYBERBIZ 做實際出倉、調倉與盤點，WMS 保留公司倉的數量。官網原生下單先扣一次、現場實際出庫再扣一次，會讓同一批貨重複扣帳。訂單回補的目的是中和前者，不是取消現場出庫。

`orders/create` 的數量是訂購數量，沒有庫存前後值；`variants/update` 是款式快照，沒有異動原因。不能把時間接近當成因果，也不能假設每筆訂單一定伴隨款式事件。POS 訂單含門市身分，不屬於公司倉官網回補。

訂單與進出倉／調倉事件以 `order`、`stock` 保存，不再落入會員處理。實體單據目前只留存，不自動增減 WMS；還沒確認它們的狀態、倉別與數量語意之前，不能用它們建立新的實體帳。

## 預設觀察，不因部署啟用庫存寫入

`CYBERBIZ_ORDER_RESTOCK_MODE` 缺省或不是精確的 `apply` 時皆為 `observe`。觀察模式只重讀、記錄及比對，不送庫存調整，也不阻擋既有同步。

`apply` 是保守的單筆校正，不是完整的跨通路庫存帳本。它只接受已辨識的官網來源、精確連結公司倉的商品／款式／SKU、正整數數量與沒有組合拆料的明細；一般贈品不因零元而漏掉。不能以相同 SKU 猜測不同門市款式的對應。

每筆工作重讀最新訂單與庫存；下單校正只處理尚未出貨且未取消的訂單。實際寫入事件超過 15 分鐘、WMS 基準在事件後被更新、連結失效、同品項有其他未確認工作，或官網與 WMS 的差額不等於本單數量時，都轉為待確認，而不是覆蓋。

官網已等於 WMS 會記為「無須調整」，不視為本程式曾回補，避免取消時反向扣除一筆根本沒做過的調整。取消校正只對已確認執行過的下單回補，且取消商品明細、來源與實際差額都吻合時執行；改單、部分退貨及未知來源不能自動套用。

## 非冪等 API 與並行限制

現有寫入是 `POST /v1/stock_adjustments` 差額 API，不是原生 PUT 絕對值或遠端 compare-and-set。

- 回補先取得同一個品項 lease，與盤點推送、官網匯入互斥。
- 實際調整使用 WMS 目標，且在 client 重讀時再次核對官網預期現值。
- POST 前必須先持久化 `applying`，再檢查過的 WMS 基準及有效 lease 才能送出。
- POST 不做 HTTP 自動重試。送出後的 timeout、驗證不符或程序中斷都轉人工確認，不能重新送相同差額。
- 只有確定尚未送出 POST 的讀取錯誤能有限重試，最多三次；每次重試仍重新查訂單、WMS 與官網。
- `order_id + phase + variant_id` 是永久業務防重鍵，跟原始 webhook 的 30 天清理分開，避免舊通知重送再加一次。
- 有 `apply` 的待處理／待確認工作時，官網快照不能覆蓋 WMS，盤點與盤點失敗補推也不能繞過。人工結案後才解除保護。

本地 lease **不能鎖住 CYBERBIZ 後台或原生訂單處理**。兩次遠端讀取之間、讀取與 POST 之間仍可能有外部異動。差額檢查不能證明異動來源；寫後重讀只是一致性驗證，不是跨系統交易。若恰好有同量、反向的異動，甚至可能無法從總數辨認。因此沒有確認庫存基準、實體單據流程及受控 smoke test 前，應維持觀察模式，不能宣稱保證不覆蓋調倉或保證瞬間一致。

## 背景工作與稽核

接收端先保存原始事件與工作，透過 `waitUntil` 執行有界 drain；沒有 ExecutionContext 的本機環境則等待工作完成。每輪最多處理五筆；cron 補救尚未送出的工作與接收途中中斷的訂單事件。受安全窗口限制而無法確認的工作，不為了補跑而放寬條件。

後台入口是「倉儲 → 操作紀錄」，資料類型「官網訂單回補」，可搜尋訂單編號／ID 或 SKU。展開明細能看到模式、原因、處理次數、官網調整前後值及 WMS 目標；未確認的調整後數量不以目標數字冒充。

紀錄查閱沿用 `wms:activity:read`；人工查核登記需 `wms:sync:trigger`，後端獨立檢查。查核動作不呼叫庫存 API，必須填說明並留下操作者。標記「已完成」代表操作者已從平台單據確認回補實際執行，會影響之後是否允許取消校正，不能只為了清掉警示而按下。

原始訂單包含個資，明細 API 與 activity 查詢不回傳它；回補帳本只保存必要的訂單、商品及調整資料。觀察期間及漏接期間的歷史訂單不會在切換模式後自動追溯回補。
