# 蝦皮訂單扣 WMS 庫存

## 要解決什麼

同一批貨在兩個通路賣，但只有一個通路會自動扣帳，於是倉庫的人補扣時會扣到重複的部分。

實際發生的情況：

```
原本庫存 200
├─ 官網賣 50 → CYBERBIZ 自己扣掉 → 系統看到 150
└─ 蝦皮賣 50 → 沒有任何地方扣

包貨時實際拉走 50 + 50 = 100 顆，於是手動扣 100
→ 150 − 100 = 50

但實際上只賣掉 100 顆，應該剩 100。官網那 50 被扣了兩次。
```

## 根因不是「庫存沒同步」

看起來像是蝦皮庫存沒跟 WMS 同步，但真正的原因是**蝦皮的銷售沒有進系統**。

因為蝦皮那 50 顆沒有任何紀錄，倉庫的人只能用「實際拉走多少」去手動補扣；而他拉走的
100 顆裡面，有 50 顆是官網的——那 50 顆 CYBERBIZ 已經扣過了。**重複的來源是手動補扣，
不是兩邊庫存數字對不上。**

所以解法是讓蝦皮的銷售也自動扣帳，讓倉庫的人不需要手動補任何東西。方向搞反的話
（先去做「把 WMS 庫存推回蝦皮」）不但解決不了重複扣，還會在 WMS 數字本來就偏低的
情況下，把錯的數字推上蝦皮賣場。

## 前置條件：先做完 Open API POC

這份設計**完全依賴** [`shopee-open-api-poc.md`](./shopee-open-api-poc.md) 已經處理好的東西：

- Shopee Open Platform 開發者帳號（`partner_id` / `partner_key`）。
- 店主完成一次賣場授權。
- Token 保管與續期：Worker 是唯一保管人、token 存 D1、15 分鐘 cron 續期、失敗告警。

**這些不在本文重複，也不應該在這裡重做一份。** POC 沒完成之前，這份設計連第一步都跑不了：
收到 webhook 之後要呼叫 `get_order_detail` 拿商品明細，那需要有效的 `access_token`。

一件要在**申請階段就想到**的事：Push 的 callback URL 是 app 設定的一部分。申請與設定
app 時就把 Worker 的 webhook 位址規劃進去，不然之後要回頭改 app 設定再重新驗證一次。

## 設計

```
蝦皮訂單狀態推播（push code 3）
  → 驗簽（HMAC-SHA256，authorization header）
  → get_order_detail 取商品明細（item_id / model_id / 數量）
  → 用外部 SKU 對到 WMS 品項
  → 扣 inventory_items.quantity，並寫一筆 activity event
```

### 對應關係用既有的表

`product_sku_mappings`（`packages/db/src/schema/wms.ts`）已經是「外部通路 SKU → WMS 品項」
的對應，而且 `external_sku` 不分通路、全域唯一。蝦皮直接用它，**不要另外開一張蝦皮專用的
對應表**——同一個實體有兩份對應表的話，兩邊會漂移，而漂移的症狀是庫存扣到錯的商品，
沒有人看得出來。

要先確認蝦皮的哪個欄位當 `external_sku`：訂單明細裡有 `item_sku`（賣家自訂貨號，對應
xlsx 的 AF/AG 欄）與 `model_id`。**優先用賣家自訂貨號**，因為那是人維護的、跨通路一致；
`model_id` 是蝦皮的內部識別碼，換商品就變。若貨號沒填，那筆要停下來標記待補，不要猜。

### 不變條件

照 `packages/db/src/wms-sync.ts` 檔頭那三條的調性辦，理由完全相同——**寧可讓一筆停在
「待處理」，也不要把數量扣到錯的商品上**：

1. 外部 SKU 在 `product_sku_mappings` 找不到 → 不扣，記成待處理，通知。
2. 一個外部 SKU 對到多個 WMS 品項 → 不扣（`external_sku` 是 unique，理論上不會發生，
   但要驗）。
3. 訂單明細缺數量或數量不合理 → 不扣，記錄原始 payload。

「待處理」要看得到、補完對應之後能重跑，否則那些單會靜靜地消失。

### 冪等

webhook 會重送，訂單狀態也會變好幾次（付款、出貨、完成），**每一次都會再推一次
code 3**。沒有防重的話同一張單會被扣很多次。

所以要記「這張單的這個品項已經扣過了」，用 `order_sn` + `item_id` + `model_id` 當鍵。
已經扣過就直接回 200，不要再扣一次。

要在哪個狀態扣也要先定：太早扣（下單就扣）會被取消單影響，太晚扣（完成才扣）則來不及
反映到撿貨。建議**付款完成時扣**，取消與退貨再加回來。

### 退貨與取消

- 訂單取消 → 把扣掉的加回來。
- 退貨（Returns API）→ 加回來，但只加實際退回倉庫的數量。
- 兩者都要跟原本那筆扣帳配對，不能只加不減或只減不加。

退貨常常跨月，所以**不要用月份當作處理邊界**，要跟著訂單走。

### 每一次變動都要留紀錄

WMS 現在每一次數量變動都會寫 activity event（見 `countItem`）。蝦皮扣帳也照做，
`actor` 標成系統來源、summary 帶訂單編號。倉庫的人看到數字變了要能查出是哪一張單。

## 反方向（把 WMS 庫存推回蝦皮）：另案，先不要做

`update_stock` 可以把 WMS 的數量寫回蝦皮，避免超賣。但這牽涉「誰是庫存的真相來源」，
是比扣帳更大的決策，而且做錯會直接影響線上銷售。

先做完扣帳、讓 WMS 的數字可信之後再談。真的要做時要注意：蝦皮的庫存分成
`normal_stock`（可寫）與它自己保留的部分（下單後鎖住，寫不到），推回去時不要覆蓋掉
保留的量。

## 待確認（做之前要有答案）

1. **用哪個欄位當 `external_sku`。** 蝦皮賣家自訂貨號目前有沒有確實填寫、跟 WMS 的 SKU
   是否一致，要先抽樣看真實資料。沒填的比例高的話，這個設計的前提就不成立。
2. **在哪個訂單狀態扣帳。** 付款完成、出貨、還是完成？取消率高低會影響選擇。
3. **既有的蝦皮訂單要不要回補。** 上線前已經賣掉的那些單不會有 webhook，要不要用
   `get_order_list` 補一次，補的話從哪一天開始。
4. **蝦皮與 CYBERBIZ 是不是同一份實體庫存。** 若兩邊各自備貨、不共用同一批貨，那扣帳的
   目標就不是同一個 `inventory_items`，整個設計要改。
