# 蝦皮訂單扣 WMS 庫存

## 要解決什麼

同一批貨在兩個通路賣，但只有一個通路會自動扣帳，於是倉庫的人補扣時會扣到重複的部分。

實際發生的情況：

```
原本庫存 200
├─ 官網賣 50 → CYBERBIZ 自己扣掉 → 系統看到 150
└─ 蝦皮賣 50 → 沒有任何地方扣

包貨時實際拉走 50 + 50 = 100 顆，於是手動扣 100
→ 150 − 100 = 50

但實際上只賣掉 100 顆，應該剩 100。官網那 50 被扣了兩次。
```

## 根因不是「庫存沒同步」

看起來像是蝦皮庫存沒跟 WMS 同步，但真正的原因是**蝦皮的銷售沒有進系統**。

因為蝦皮那 50 顆沒有任何紀錄，倉庫的人只能用「實際拉走多少」去手動補扣；而他拉走的
100 顆裡面，有 50 顆是官網的——那 50 顆 CYBERBIZ 已經扣過了。**重複的來源是手動補扣，
不是兩邊庫存數字對不上。**

所以解法是讓蝦皮的銷售也自動扣帳，讓倉庫的人不需要手動補任何東西。方向搞反的話
（先去做「把 WMS 庫存推回蝦皮」）不但解決不了重複扣，還會在 WMS 數字本來就偏低的
情況下，把錯的數字推上蝦皮賣場。

## 前置條件：先做完 Open API POC

這份設計**完全依賴** [`shopee-open-api-poc.md`](./shopee-open-api-poc.md) 已經處理好的東西：

- Shopee Open Platform 開發者帳號（`partner_id` / `partner_key`）。
- 店主完成一次賣場授權。
- Token 保管與續期：Worker 是唯一保管人、token 存 D1、15 分鐘 cron 續期、失敗告警。

**這些不在本文重複，也不應該在這裡重做一份。** POC 沒完成之前，這份設計連第一步都跑不了：
收到 webhook 之後要呼叫 `get_order_detail` 拿商品明細，那需要有效的 `access_token`。

一件要在**申請階段就想到**的事：Push 的 callback URL 是 app 設定的一部分。申請與設定
app 時就把 Worker 的 webhook 位址規劃進去，不然之後要回頭改 app 設定再重新驗證一次。

## 設計

```
蝦皮訂單狀態推播（push code 3）
  → 驗簽（HMAC-SHA256，authorization header）
  → get_order_detail 取商品明細（item_id / model_id / 數量）
  → 用外部 SKU 對到 WMS 品項
  → 扣 inventory_items.quantity，並寫一筆 activity event
```

### 對應關係用既有的表

`product_sku_mappings`（`packages/db/src/schema/wms.ts`）已經是「外部通路 SKU → WMS 品項」
的對應，而且 `channel + external_sku` 用來識別不同通路的 mapping。蝦皮直接用它，**不要另外開一張蝦皮專用的
對應表**——同一個實體有兩份對應表的話，兩邊會漂移，而漂移的症狀是庫存扣到錯的商品，
沒有人看得出來。

`external_sku` 用**蝦皮的「商品ID_規格ID」**（xlsx 的 AC 欄，例如
`26491332332_216256146329`）。

原本想用賣家自訂貨號（AF／AG 欄），但抽 2026-07 的 774 列看過，**兩欄的填寫率都是 0%**，
42 個款式沒有一個有填，這條路現在走不通。要改用貨號的話得先請人到蝦皮後台補完 42 個
款式，補完之前 `商品ID_規格ID` 是唯一能用的鍵。

代價是商品下架重上會換 ID、對應跟著失效。這可以接受，因為失效會被下面的第 1 條不變條件
擋成「待處理」，不會扣到錯的商品。

### 報表那一側也要改成同一個鍵

**這是動工前要先做完的前置改動，不是這份設計的附帶效果。**

蝦皮報表現在送進 D1 的 `sku` 只有**商品ID**，所有規格合併成一列
（`tools/shopee-sales-report-export/lib/xlsx.mjs` 的 `salesDaily`，取 Z 欄）。扣庫存要的
卻是**分規格**的鍵，因為不同規格是不同的實體商品：

```
🎉三瓶優惠🎉 液體皂 / 醬釀黑豆   203
🎉三瓶優惠🎉 液體皂 / 雪松蜂漿   147
🎉三瓶優惠🎉 液體皂 / 花漾珍珠    64
```

這是三種不同的皂，扣庫存不能合在一起。

`product_sku_mappings` 以 `channel + external_sku` 唯一。報表現在使用
`商品ID_規格ID`，但為了讓既有設定可以平滑升級，解析時找不到完整鍵會回退查找舊的
`商品ID`；若同時存在兩者，完整的規格鍵優先。

所以報表那一側改成一樣的 `商品ID_規格ID`：

- 改 `xlsx.mjs` 的 `salesDaily`，鍵從 Z 欄改成 Z 欄 ＋ AB 欄（規格ID）。
- 既有的蝦皮月資料重新匯入一次即可。`insertReportSalesMonthly` 會先刪掉該 scope 該月的
  所有列再寫入，所以舊鍵不會留下孤兒列，不需要寫 migration。
- 既有只用商品 ID 建立的蝦皮對應可以先沿用；新增或編輯時建議改用完整的商品 ID＋規格 ID，讓不同規格可以分別對應。

xlsx 的三張工作表不動——`業績計算` 依訂單、`商品銷售統計` 依 Z＋AA，兩者都跟 D1 的鍵無關，
所以 [`shopee-open-api-poc.md`](./shopee-open-api-poc.md) 的四個驗收數字不受影響。

順帶一提，報表匯入本來就是**沒對應就整批 422 失敗**
（`apps/api/src/cyberbiz-report-ingest.ts` 的 `unmapped_product`）。所以蝦皮的對應不是這次
才要建的東西，而是現在就存在、只是鍵要換。動手前要先看正式環境裡現有的是哪一種鍵。

### 組合包要拆成用料

一個蝦皮款式不等於一個 WMS 品項的一個單位。以 2026-07 為例，42 個款式裡有 13 個是組合包，
而且**佔了總數量 2237 的 2023（90%）**。最大的那個「買5送二再送一」實際出貨是
**5 個香皂 ＋ 2 個旅行皂 ＋ 1 個起泡網**——三種不同商品，不是同一個商品乘以 8。

所以要另外一張用料表。**不要把 `product_sku_mappings` 改成一對多**：

```
product_sku_mappings        （不動）external_sku → 一個 WMS 品項
product_bundle_components   （新增）mapping → 多個品項 × 數量
```

`product_sku_mappings` 現在唯一的用途是報表匯入時把外部 SKU 對成商品名稱與分類
（`resolveProductSkus`，見 `apps/api/src/cyberbiz-report-ingest.ts`）。它回答的是「這個
外部 SKU 顯示成哪個商品」，跟「賣掉這一組要扣哪些料」是兩個問題。改成一對多的話報表會
壞掉——它要顯示的是「買5送二再送一賣了 1551 組」，不是拆開的三個品項。

新表的形狀：

| 欄 | 說明 |
|---|---|
| `mapping_id` | → `product_sku_mappings`，`ON DELETE CASCADE` |
| `inventory_item_id` | → `inventory_items`，**`ON DELETE RESTRICT`** |
| `quantity` | 一組扣幾個 |
| | `UNIQUE(mapping_id, inventory_item_id)` |

`inventory_item_id` 刻意用 RESTRICT 而不是既有那張表的 CASCADE：商品被刪掉時如果用料靜靜
消失，組合包就會少扣，而且沒有人看得出來——那正是這整份設計最想擋掉的失敗模式。

扣帳的解析順序：**有用料就照用料扣，沒有用料就扣 `inventory_item_id` 一個。** 這樣單品
不必建用料，2026-07 的 42 個款式只有 13 個要建。

這是純新增的 migration，不重建 `product_sku_mappings`，避開 D1 上 `DROP TABLE` 連坐刪除
那個坑（見 `CLAUDE.md` 的禁止事項）。

用料表要有地方編輯，所以 WMS 那頁要加對應的 UI。

### 組合內容會變，所以扣帳要寫快照

組合包的內容會換（這個月送起泡網、下個月換別的）。因此**不要在退貨或重算時回頭查用料表**，
那時查到的是現在的組成，不是當初出貨的組成。

作法是**扣帳當下就把展開結果寫進扣帳紀錄**：這一筆訂單、這個款式，實際扣了哪些品項、
各幾個。用料表只保存「現在的組成」，歷史留在扣帳紀錄裡。退貨依紀錄回沖，不重新展開。

不採用「用料表加生效日期」的版本化作法：那要求改組成的人記得新增一版而不是直接改，
維護成本高，而且一樣擋不住「1 號換組成、10 號才更新資料」的落差。快照至少讓那段期間
受影響的訂單查得出來、補得回去。

報表與庫存扣帳都共用同一份 mapping。一般商品只走 `product_sku_mappings` 的一對一對應；任何通路的報表若 mapping 有用料，匯入 D1 時會依用料數量展開成各 WMS SKU，讓商品銷售查詢能反映實際銷售的單品數量。蝦皮來源的 salesAmount 維持 0，不能把組合包金額複製到每個元件。組合內容更新後只影響之後重新匯入的報表，已產出的月份資料仍是當時的快照。

### 不變條件

照 `packages/db/src/wms-sync.ts` 檔頭那三條的調性辦，理由完全相同——**寧可讓一筆停在
「待處理」，也不要把數量扣到錯的商品上**：

1. 外部 SKU 在 `product_sku_mappings` 找不到 → 不扣，記成待處理，通知。
2. 一個外部 SKU 對到多個 WMS 品項 → 不扣（`external_sku` 是 unique，理論上不會發生，
   但要驗）。
3. 訂單明細缺數量或數量不合理 → 不扣，記錄原始 payload。

「待處理」要看得到、補完對應之後能重跑，否則那些單會靜靜地消失。

### 冪等

webhook 會重送，訂單狀態也會變好幾次（付款、出貨、完成），**每一次都會再推一次
code 3**。沒有防重的話同一張單會被扣很多次。

所以要記「這張單的這個品項已經扣過了」，用 `order_sn` + `item_id` + `model_id` 當鍵。
已經扣過就直接回 200，不要再扣一次。

要在哪個狀態扣也要先定：太早扣（下單就扣）會被取消單影響，太晚扣（完成才扣）則來不及
反映到撿貨。建議**付款完成時扣**，取消與退貨再加回來。

### 退貨與取消

- 訂單取消 → 把扣掉的加回來。
- 退貨（Returns API）→ 加回來，但只加實際退回倉庫的數量。
- 兩者都要跟原本那筆扣帳配對，不能只加不減或只減不加。

退貨常常跨月，所以**不要用月份當作處理邊界**，要跟著訂單走。

### 每一次變動都要留紀錄

WMS 現在每一次數量變動都會寫 activity event（見 `countItem`）。蝦皮扣帳也照做，
`actor` 標成系統來源、summary 帶訂單編號。倉庫的人看到數字變了要能查出是哪一張單。

## 反方向（把 WMS 庫存推回蝦皮）：另案，先不要做

`update_stock` 可以把 WMS 的數量寫回蝦皮，避免超賣。但這牽涉「誰是庫存的真相來源」，
是比扣帳更大的決策，而且做錯會直接影響線上銷售。

先做完扣帳、讓 WMS 的數字可信之後再談。真的要做時要注意：蝦皮的庫存分成
`normal_stock`（可寫）與它自己保留的部分（下單後鎖住，寫不到），推回去時不要覆蓋掉
保留的量。

## 待確認（做之前要有答案）

1. **要不要先去蝦皮後台補齊 42 個款式的賣家自訂貨號。** 補了就能用人維護、跨通路一致的
   貨號當鍵；不補就用 `商品ID_規格ID`，代價是重新上架會換 ID。
2. **在哪個訂單狀態扣帳。** 付款完成、出貨、還是完成？取消率高低會影響選擇。
3. **正式環境的 `product_sku_mappings` 現在有哪些蝦皮對應、用的是哪種鍵。** 換鍵之前要先
   看清楚，換完要重匯受影響的月份。
4. **既有的蝦皮訂單要不要回補。** 上線前已經賣掉的那些單不會有 webhook，要不要用
   `get_order_list` 補一次，補的話從哪一天開始。
5. **13 個組合包的用料由誰建、什麼時候建。** 沒建完之前那些款式只能停在待處理，
   而它們佔了 90% 的數量，等於整條扣帳幾乎不會動。
6. **蝦皮與 CYBERBIZ 是不是同一份實體庫存。** 若兩邊各自備貨、不共用同一批貨，那扣帳的
   目標就不是同一個 `inventory_items`，整個設計要改。
